# FroneCamera 仓库修改意见与实施验收清单

日期：2026-10-19  
审查对象：`baolinv0/FroneCamera`，实际分支 `agent/openai-auto-pairing-final`  
固定基线：`2423af87b5029f888b004f8cbff30d6b540094fd`  
性质：基于已完成的源码、设计文档和测试文件静态审阅形成的修改建议；本文件不宣称已经修改代码、运行仓库测试或完成新一轮模型评测。

## 1. 总体判断

该项目适合作为“可追溯的前置摄像头对比评测系统”底座。匿名评图、多轮复核、结构化结果、报告导出和外部资料后置等设计值得保留。当前主要问题是：设计层已描述较完整的证据链，实际运行链仍以较粗的图像统计和少量跨场景规则驱动结论。仅改报告模板，无法消除证据不足或错误升级的问题。

优先顺序应为：先修复输入与裁决的可信性，再补齐跨场景归纳，最后扩展自动化、模型引导和界面。先把“看到了什么、依据是什么、可以推到哪一步”做实，不先扩大评分体系或增加模型调用次数。

本次建议仅发布文档，不附私人照片、原始人像、私有数据链接、鉴权信息或个人工作记录。

## 2. 设计能力与实际运行能力分开记账

| 层级 | 已观察到的能力 | 使用边界 |
|---|---|---|
| 设计文档 | 多维评价、证据链、反例、跨场景策略、硬件与外部来源隔离 | 属于目标和规范，不能视为运行验收 |
| 实际调用链 | API/worker/workflow 调用 `EvaluationPipeline`，生成图像分析、复核、裁决及报告 | 应以该调用链为修改和回归测试入口 |
| v2 数据结构 | `core/models_v2.py`、维度定义、持久化与完整性相关结构 | 有 schema 不等于核心推理已接入运行链 |
| 图像分析 | 整图统计、最大人脸区域、若干细节/噪声代理量 | 不能覆盖群像、真实噪声、色彩准确性等完整命题 |
| 跨场景总结 | 相对整图亮度、近白像素占比两类规则 | 不能直接代表肤色、影调塑形、后排清晰度等完整调校策略 |
| DOCX 导出 | 总览、证据覆盖、逐场景、归因和边界等骨架已编码 | 测试中的样例画像不等于真实运行已经输出该水平的归纳 |

建议在 `docs/implementation-status.md` 增加“设计已定义 / 代码已实现 / 运行链已接入 / 测试已通过 / 真实样本已核验”五列。任何能力只有对应证据齐全，才能升级状态。

## 3. P0：影响结论正确性的阻断问题

以下问题应先于任何正式设备排名、品牌画像或自动参数建议修复。

### P0-01 色彩管理与亮度定义

- 现象：`load_rgb` 执行 EXIF 方向处理和 RGB 转换，未见 ICC 转换。直接对编码 RGB 加权的亮度量也不等于线性光亮度。
- 风险：不同色域输入产生颜色比较偏差；同名亮度统计口径不一致，污染跨设备趋势。
- 修改：保留原文件；记录 ICC、方向、位深、容器和渲染方式；使用显式 ICC 转换得到统一 SDR 分析图。保留“编码亮度 Y′”和“线性亮度 Y”两个不同字段及公式，禁止混用。无 ICC 时输出明确假设和状态；不把格式转换当作色彩校准。
- HDR 边界：明确分析基图、gain map 或指定 HDR 渲染版本。只分析 SDR 基图时不得宣称原生 HDR 显示能力。
- 测试：同一色块分别编码为受支持的 sRGB/P3 配置后，转换结果符合预先冻结的数值容差；EXIF 1–8 全覆盖；灰阶的 Y 与 Y′符合公式；缺失/损坏 ICC 可解释降级；多图容器选择可重复；预览和分析输入具有同一渲染记录。
- 完成标准：所有进入评测的资产都有可追溯色彩/方向记录；不支持的输入停止有关颜色命题，而不是悄悄按 sRGB 通过。
- 预计投入：2–3 工程人日；收益：消除源头混杂，所有后续统计共享可靠输入。

### P0-02 多人脸与原生细节证据

- 现象：目前选择最大 Haar 人脸；VLM 输入以整图缩放为主。后排或较小人脸可能未进入分析。
- 风险：把“主脸好”写成“群像好”；缩图掩盖失焦、涂抹、噪声和边缘处理。
- 修改：记录所有有效人脸及其角色（前景/后排/边缘/未知），允许人工校正；区分整图、等显示尺寸和原生裁剪三类证据。人脸匹配仅限同一拍摄组中经确认的对应人物，不进行跨数据集身份识别。人脸检测失败不等于没有人物。
- 测试：单人、双人、前后景、边缘部分人脸、遮挡、侧脸、无人、检测失败；裁剪坐标和 EXIF 转换联动；原生裁剪逐像素重建一致；模型可见证据清单必须记录实际使用的整图/裁剪。
- 完成标准：群像结论能指向每个被讨论的人脸；未观察到后排原生细节时，不允许自动通过群像清晰度判断。
- 预计投入：2–4 人日；收益：覆盖前摄核心失败模式，避免仅主脸驱动的系统性遗漏。

### P0-03 模型一致性不能代替真实支持

- 现象：场景裁决按设备与维度匹配复核项，没有充分核对陈述方向；`objective_support` 固定为 1。现有同模型多轮分析不具备独立模型家族的证据强度。
- 风险：“更亮”和“更暗”可能被统计成同维度一致；没有客观支持的观察也得到确定性加成。A/B 标签易被误读为校准后的置信度。
- 修改：结构化保存目标区域、属性、比较对象、方向、强度、证据 ID、适用条件；复核分为支持/反对/无法判断/不同命题。客观支持由具体测量和其适用性产生；没有指标时为 unknown，不填满分。分别呈现观察质量、支持范围、评审分歧，暂不压成一个可信度分数。
- 测试：同设备同维度但方向相反必须进入冲突；肤色偏移与亮度变动不得合并；指标缺失保持 unknown；主评与复评相同模型须记录依赖关系；完全不可比样本不能获可发表等级；确认未观察区域无法通过模板自动填充。
- 完成标准：每条正式判断能回指可见证据；未校准的分值明确称规则分数，不称准确率或可信概率。
- 预计投入：3–5 人日；收益：防止系统自信地输出无支持结论。

### P0-04 跨场景反例和场景独立性

- 现象：策略归纳当前主要采用整图亮度与近白像素规则；按现有得分与分支关系，支持达到阈值后，较多反例不一定能阻止强结论。该判断来自静态逻辑，不是已运行的失败测试。
- 风险：少量支持加大量反例仍被写成稳定策略；同一场景多个角度被当成独立重复。
- 修改：跨场景命题必须带挑战条件、方向、支持/反例/未知/不可比集合、场景家族 ID。先按家族归并，再描述条件性倾向；存在关键反例时写出边界，不能仅以支持数量覆盖。不得把某个输出更暗直接认定为暗光采集。
- 测试：3 个支持、21 个反例不能输出无条件 CONFIRMED；同一物理环境 10 个相近位置不等于 10 个独立环境；互相矛盾的区域表现不能压成全图单一方向；家族去重前后证据集合可检查；零支持不允许生成画像。
- 完成标准：所有源级画像同时显示支持、反例、范围与未知。暂不强行设“几个场景就证明普遍规律”的固定门槛。
- 预计投入：3–5 人日；收益：把逐图日志转为可审计、有限度的归纳。

### P0-05 外部资料绑定与污染隔离

- 现象：外部对照部分按 `claim_statement` 文本匹配；不同设备相同模板陈述可能串联。外部检索以标题/摘要片段为主，来源域名等级不等于证据独立性。
- 风险：A 设备的外部资料进入 B 设备结论；厂商宣传或总体口碑被误当作本照片的独立验证。
- 修改：使用不可变 `claim_id`，连同 `device_id`、`scene_id`、`attribute`、版本绑定；内部视觉结论冻结后才查外部资料。外部记录原文出处、适用机型/模式/场景、直接证据或一般背景、来源依赖。外部支持不能回写伪装成原始盲评。
- 测试：两个设备使用相同陈述文字，外部证据不得互串；旧版本证据不能静默匹配新命题；只有标题或总体机型评价时不得升级为本图验证；同源转载不算多个独立来源；品牌解盲前不可见外部标签。
- 完成标准：每条外部对应有唯一对象和可核验来源，无法对照时明确保留 unknown。
- 预计投入：1–2 人日；收益：防止设备错配与确认偏差。

## 4. P1：决定报告是否有用的功能修改

### P1-01 以输入挑战而非成片风格组织场景

推荐主类别：均匀光、高反差/逆光、混合/有色光、多人/景深、低光/夜景、强光/反射。允许主类别加副标签；场景家族独立于场景位置。没有现场元数据时，分类应标记“依据画面判断”，不能把输出亮度阈值当作实际照度。

修改点：将 `audit_scene` 的统计输出改为“成片特征”；输入挑战由确认的拍摄记录或有依据的人工/模型标注产生。场景配对保留用户确认，顺序自动匹配只作候选，不用低层图像相似性否定已经确认的同场景关系。

验收：同一输入挑战的明亮/暗调渲染版本不因亮度变化而自动改类；每个分组能列出所有源、缺失项和配对依据；缺一张时不会导致后续全体序号错移；DNG 占位和预览提取状态分别记录。

投入：1–2 人日。收益：报告章节真正围绕拍摄难点，减少结果反向定义条件的循环论证。

### P1-02 报告由命题驱动，保留完整逐图附录

报告推荐结构：
1. 一页总结：最重要的判断、适用条件和未解决项。
2. 前摄的目标冲突：脸亮与塑形、肤色与环境、洁净与细节、主脸与群像、夜间可读性与氛围。
3. 数据与方法边界、场景挑战矩阵。
4. 按挑战展开：结论 → 并排证据 → 收益与代价 → 反例 → 适用范围。
5. 各源画像：优先目标、重复优势、代价、失败条件、反例；没有足够重复证据时不强写画像。
6. 可疑技术环节及最小排查实验。
7. 工程优先级与需要人工裁决的内容。
8. 全量逐图、区域、统计及引用附录。

十维检查表应作为底层覆盖要求，不机械变成十章同等篇幅。清晰地区分风格偏好、可见缺陷与未知机制。可明确评价“后排人脸过软影响可辨认”，无需假装已经知道是 AF、降噪还是多帧处理造成。

验收：每条摘要命题有证据 ID；正文关键命题均有反例搜索结果（包括未找到但搜索范围有限）；不得用空泛“整体自然”替代可定位证据；附件保留全部样本，正文只选择能支撑命题的代表和反例。图文和机器 JSON 必须由同一数据对象生成。

投入：3–5 人日。收益：解决当前可读性、总结和结论不足的主要问题。

### P1-03 报告字段契约与端到端验收

静态观察提示字段可能不一致：偏差模块输出 `reasons/recommended_actions`，DOCX 读取 `reason/recommendation`；归因模块输出 `statement/candidate_causes`，DOCX 读取 `observable_effect/rationale`。这是需要复现确认的风险，不写作已经发生的运行缺陷。

修改：统一版本化数据契约；禁止静默用泛化文本替代缺失关键字段；对历史格式使用显式迁移；建立真实结构的最小报告 fixture，包含缺失源、反例、unknown、多脸和冲突，不能只用彩色占位图。

验收：从入口到导出一条完整离线链；所有可见段落对应预期字段；所有图片、链接、交叉引用有效；导出后实际渲染逐页检查溢出、图注、字体和分页；仅测试文档可打开不算合格。PDF/DOCX 与 HTML 的命题、图像和边界保持一致。

投入：1–3 人日。收益：避免正确数据在报告层丢失，明确自动报告的可交付标准。

### P1-04 机制归因从“命名原因”改成“竞争假设”

EXIF 某字段存在不等于它支持特定机制；整机第一张照片的元数据也不能支持其他场景的归因。机制模块应以命题证据所在照片的元数据为准，输出现象、候选机制、替代原因、支持/反对证据以及最小区分实验。无 RAW、重复拍摄或消融时，不能把噪声/软化/光晕直接归因于具体 ISP 算法或硬件。

测试：元数据归属错误必须拒绝；没有快门值但有键名不能算已知；同一软化现象至少允许对焦、运动、降噪/融合、压缩等竞争解释；不支持的硬件信息不得进入既定原因。

投入：1–2 人日。收益：技术解释可服务排查，不制造“逆向出了 ISP”的错觉。

### P1-05 模型感知能力与相机测评成绩分开验收

相机测评回答照片表现；模型能力测试回答评图是否可靠。应单列模型版本、提示词、输入分辨率、裁剪策略、重复调用和人工参照。基础任务包含方向相反的对照、相同图、顺序互换、水平翻转、区域定位、影调与风格偏好分离；评图能力不能由最终报告流畅程度证明。

首次先用少量覆盖性样本验证协议，再冻结评测集。人工标注应记录分歧并允许无法判断；不把同一模型的自我复核视为人类真值。人工人数和统计方法在实测前登记，未完成时只报告模型内部一致性。

投入：工程接入约 2–4 人日，人工评审另计。收益：为“影像调校助手哪些信息能用”建立独立依据。

## 5. P2：在基础链验收后扩展

| 项目 | 具体修改 | 验收要求 | 预计投入 |
|---|---|---|---|
| 模型引导信号 | 输出区域、属性、方向、目标范围、禁止变化和风险，不输出没有证据的精确参数 | 弱证据只作候选；冲突或机制未知时可停止建议；结果需独立复评 | 3–5 人日 |
| 小规模闭环 | 原图保留为对照；执行策略采用固定、模型选候选、模型诊断参数、独立反馈四臂，详见完整计划第 8 节；保存每轮变化 | 在预登记质量目标上改善且无结构/肤色/光照副作用；失败回滚，不以模型自己打分作为唯一奖励 | 3–5 人日 |
| 校准与统计 | 按场景家族分割开发/验证，呈现覆盖、分歧和不确定性 | 调阈值不使用最终验证集；支持/反例分母透明；无独立性时不滥用置信区间 | 2–4 人日 |
| 交互与复核队列 | 展示证据和冲突，支持修正 ROI、分类及命题 | 人工修改有版本与审计记录，不覆盖原始结果 | 2–4 人日 |
| 性能优化 | 缓存色彩转换/裁剪，按任务路由整图与细节，记录调用成本 | 缓存键包含输入哈希、转换、模型和提示版本；性能优化不减少强制证据覆盖 | 1–3 人日 |

以上为工作量量级估算，不是承诺工期；共享数据结构、既有实现程度和人工评审安排会显著影响总投入，不应简单逐项相加。

## 6. 推荐代码分工与迁移顺序

1. 输入层：`imaging.py`、`dataset.py` 负责方向、色彩、原生像素、匹配与角色记录；避免向图像加载器混入评分策略。
2. 证据层：统一资产、ROI、实际查看记录、测量定义和版本。兼容已有 v2 结构，先补适配器，不建立第二套无法互通的数据格式。
3. 裁决层：`adjudication.py` 与 `pipeline.py` 消除硬编码支持，增加命题一致性和冲突门禁。
4. 归纳层：`strategy.py` 以场景家族和条件命题归纳；从亮度/高光扩展到脸部塑形、肤色关系、群像、细节及反射，逐类验证，禁止用模板伪造丰富度。
5. 归因/外部层：`attribution.py`、`corroboration.py` 保持视觉冻结和强对象绑定。
6. 展示层：`docx_reporting.py` 与其他格式共享经过验证的报告模型。

每个阶段先建立失败用例，再实现并运行回归；仅在该阶段证据门禁通过后，扩大真实数据运行。完整重构不是前提，可以围绕现有入口逐步替换。

## 7. 一次可执行的交付清单

- [ ] 固定分支与提交，记录当前运行入口和能力状态。
- [ ] 生成不含私人图像的测试 fixture，覆盖色域、多脸、缺失、反例和字段不一致。
- [ ] 完成 P0，并实际运行新增回归；报告命令、版本与结果。
- [ ] 用小批已授权样本做集成检查；每个输入挑战至少有一个可核验案例，不声称因此具有统计代表性。
- [ ] 冻结报告数据契约和摘要命题门禁。
- [ ] 全量运行后先审查证据与反例，再生成主文。
- [ ] 实际渲染导出稿，逐页检查；交付报告、结构化记录、覆盖矩阵和已知限制。
- [ ] 仅在人工参照与校准足够后讨论“模型可作为优化引导信号”的强结论。

停止条件：输入色彩状态不明却需要颜色比较、关键人脸未被观察、同一命题严重冲突未裁决、外部证据对象不明、导出丢失关键字段时，暂停受影响结论；不要求无关场景全部停机。
